# 02 · 为什么 NAT 就能绕开「2 台设备」限制

> 这篇是给「为什么这样做有效」的完整推导 + 本机实测命令与结果。
> 所有 IP/MAC 已脱敏成占位符或网段写法。

## 1. 「设备数」是在哪里数的

先明确一件事：**校方数的是「认证会话」，不是「物理设备」。**

门户认证完成后，网关给这次认证建立一条会话记录，回执里的 `userIndex` 就是它的主键，内容形如：

```
<nasip>_<认证客户端的 WAN 侧 IP>_<账号>
```

同时 `getOnlineUserInfo` 里明确带着这次会话的：

- `userMac` —— **认证主体的 MAC**
- `userIp` —— **认证主体拿到的校园网 IP**

实测这两个值分别对应**路由器**：`userMac` 就是路由器在 LAN 侧的同一个 MAC（在路由器局域网的 ARP 表里能看到它对应网关地址），`userIp` 是校园网分给路由器 **WAN** 的 10.x 地址。

所以「一个账号最多 2 台设备」= **最多 2 条并发认证会话**。终端（手机/电脑）根本不参与这个计数。

## 2. 于是方案就是一句话

**让路由器去认证一次，剩下的设备全部藏在 NAT 后面。**

```
                 ┌─ 手机     ┐
未认证的终端 ──►  │ 电脑     │ ──► 路由器 NAT ──► WAN: 1 个 MAC + 1 个校园网 IP ──► 校园网网关
                 └─ 平板 …    ┘                   （网关侧只数到 1 台设备）
```

- 终端自己不登录门户 → 网关不知道终端的存在；
- 终端换 MAC、开 MAC 随机化、今天加 5 台设备 → 网关看到的还是路由器那一个 MAC；
- 账号配额只被占用 1 个（第 2 个留给「万一你要让某台设备自己认证」的情况，通常用不到）。

**关键点：认证必须在路由器上完成，而不是在每台终端上。** 只要终端不自己去登录门户，它们就是「NAT 后面的隐身设备」。

## 3. 为什么不用刷机 / 换固件

设备限制的计数发生在**认证网关侧**，而网关只能看到 WAN 侧的 MAC/IP。原厂固件的路由器就已经在做 NAT 了，能力足够，不需要：

- 不需要 802.1X 客户端（本环境是 Web/eportal 认证，不是 802.1X）；
- 不需要第三方固件、不需要装插件；
- 不需要在路由器上跑常驻的认证客户端（认证是**一次性**的，`keepaliveInterval=0`）。

需要改固件的场景只有一个：校方部署了**基于流量特征的多设备检测（DPI）**，那时 NAT 的「隐身」会被穿透 —— 但那是另一个问题，见 [03-detection-and-risks.md](03-detection-and-risks.md)，本仓库不给刷机步骤。

## 4. 本机实测命令与结果

### 4.1 三条路径的出口公网 IP 互不相同 → 说明走的是不同上行

```bash
curl --interface <路由器LAN侧地址> -s http://ip.3322.net   # 183.69.x.x   ← 校园网出口
curl --interface <手机共享侧地址>   -s http://ip.3322.net   # 123.147.x.x  ← 手机流量出口
curl                              -s http://ip.3322.net   # 123.147.x.x  ← 默认路由（手机）
```

结论：路由器走的是校园网，**不是**靠电脑/手机转发出去的；两条上行彼此独立。

### 4.2 认证前 vs 认证后

| 检查 | 认证前 | 认证后 |
|---|---|---|
| `curl http://connect.rom.miui.com/generate_204`（走路由器） | 被劫持，返回门户跳转脚本 | `204` |
| `curl http://ip.3322.net`（走路由器） | 返回 `<script>top.self.location.href='…/eportal/index.jsp?…'</script>` | 返回公网 IP |
| `curl https://www.baidu.com`（走路由器） | 跳门户 | `200` |
| `getOnlineUserInfo` | `result: fail`「用户可能已经下线」 | `success`，带 `userIp`/`userMac` |

### 4.3 网关 ARP 里只有一个 MAC

在路由器下面查 ARP / 邻居表，`192.168.31.1`（网关）对应的 MAC 与 `getOnlineUserInfo` 回执里的 `userMac` 是**同一个** —— 这条链路就是「校方看到的唯一设备」。

## 5. 多线路时的调试技巧：绑定源地址，不动默认路由

真实场景：电脑一边用手机 USB 共享上网（默认路由优先级更高），一边网线又连着路由器。这时直接访问 `10.x`（校园网内网）会走手机那条路 → 超时，你会误以为「门户挂了」。

**错误做法**（虽然网上教程常见）：`route add 10.0.0.0 mask 255.0.0.0 <路由器网关>` —— 这是**全局改路由**，一不小心就把正在用的默认路由/手机共享搞坏（实测中就出过「网被断了」的事故）。

**正确做法**：只让这一次请求绑定路由器那条网卡的源地址：

```bash
curl --interface <路由器LAN侧地址> http://10.253.3.84/     # 实测：返回 302 → 门户
python eportal_login.py login --config config.local.json --source-ip <路由器LAN侧地址>
```

实测效果：绑定源地址的请求走路由器（能到 `10.253.3.84`），系统路由表和默认路由**完全没动**，正在上网的那条线毫发无损。

> 同理，`ping -S <源地址>` 也可以用来做对照测试（本环境门户/网关对 ICMP 不响应，会显示超时，属正常）。

## 6. 想让电脑优先走路由器而不是手机

两条路（都需要你手动操作，脚本不改网卡设置）：

1. **拔掉手机 USB 数据线** —— 立刻生效，最省事；
2. **改网卡跃点**，让路由器那条优先级更高：
   - GUI：`ncpa.cpl` → 右键路由器那块网卡 → 属性 → IPv4 → 高级 → 取消「自动跃点」→ 接口跃点填 `10`；
   - 命令行（需管理员）：
     ```powershell
     Set-NetIPInterface -InterfaceIndex <网卡序号> -InterfaceMetric 5
     ```
     （`Get-NetIPInterface -AddressFamily IPv4` 可查序号。脚本本身**不会**替你改这些。）

---

结论回顾：**设备限制的本质是并发认证会话数；把认证集中到路由器、把终端藏到 NAT 后面，限制就解除了** —— 全程不刷机、不改路由表、不用第三方固件。
